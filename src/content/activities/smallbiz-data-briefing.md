**Next.js, 공공 API, 레터 CMS, 분석 이벤트 · 데이터 제품 MVP**

## 제품의 문제와 초기 구성

소상공인이 자기 지역의 상권 변화와 지원사업, 당일 준비에 필요한 신호를 빠르게 읽도록 “오늘의 장사 데이터”를 구성했습니다. 지역·업종 탐색, 상권 비교, 지원사업 필터, 손익분기점 계산기, 데이터 방법론 페이지를 만들고, 기능을 늘리는 것보다 운영 판단에 필요한 정보를 짧은 브리핑으로 묶는 방향을 검토했습니다.

## 데이터 상태를 제품에 반영

전국 공통 데이터와 지역별 상세 데이터의 범위가 다르고 갱신 주기도 달라, 자료를 같은 시점의 현황처럼 보이지 않게 하는 것이 중요한 과제였습니다. 공식 API 실시간 연결, 공식 sample, 저장 스냅샷의 상태를 나눴고 기준 시각과 설명을 고쳤습니다. 서울 sample 키가 요청 장소와 무관하게 광화문·덕수궁 자료를 반환하는 제약과, 분기 추정매출이 매일 갱신되는 자료가 아니라는 점을 화면과 문서에서 구분했습니다.

## 레터와 운영 구조

운영 측면에서는 레터의 초안·검수·발행과 관리자 권한, 예약 발행, 방문·체류 이벤트, A/B 실험, SEO 구조를 다뤘습니다. 관련 API와 관리자·레터 코드는 존재하지만 실제 운영 서비스와 외부 설정을 모두 연결한 검증이나 통계적 실험 성과까지 완료했다는 뜻은 아닙니다. 경쟁 분석과 페르소나 검토는 제품 방향을 정하기 위한 가설이며 실제 고객 인터뷰 결과와 구분했습니다.

## 주변 탐색과 오류 처리

주변 탐색에서는 선택 지역의 블로그 검색과 시·도 행사 정보를 연결했습니다. 잘못된 검색 행이나 URL 하나 때문에 정상 결과 전체가 사라지지 않도록 처리하고, http/https만 허용하며 중복을 제거했습니다. 이것은 가게 좌표의 반경 검색이나 실제 방문객 추정, SNS 전수 수집 기능이 아닙니다.

## 현재 제공 범위와 검증

일부 상권 비교 화면에는 인터페이스 검증용 데모가 남아 있고, 정식 API 키와 운영 환경에 따라 제공 범위가 달라집니다. 10월 9일 인수인계의 로컬 테스트·lint·build 통과와 운영 배포 확인은 별개였습니다. 유입·재방문·매출 효과는 확인하지 않았으며 이후에는 자기 지역 저장과 브리핑 효용을 관찰하는 것이 필요하다고 정리했습니다.
